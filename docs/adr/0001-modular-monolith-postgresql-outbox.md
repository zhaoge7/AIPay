# ADR-001：模块化单体、PostgreSQL 与 Transactional Outbox

- 状态：已接受
- 日期：2026-08-26
- 关联决策：`D-015`

## 背景

AIPay MVP 由单人开发，需要在较短周期内验证 Agent 购买 API、MCP 和 Skill 服务的完整闭环。系统处理授权、预算、报价、支付、交付、退款和审计，必须优先保证事务一致性、幂等性、可追踪性和安全边界。

支付执行不能依赖 LLM 的非确定性输出。业务状态与待发送事件不能出现一边提交、一边丢失；外部支付通道的超时和重试也不能造成重复扣款。

当前负载和团队边界尚未得到真实业务验证，因此不应提前承担微服务、分布式事务和独立消息系统的开发及运维成本。

## 决策驱动因素

- 单人团队需要低开发成本和可本地复现的调试路径。
- 核心状态变化需要 PostgreSQL 事务、唯一约束和行级并发控制。
- API 请求、后台重试和外部回调必须使用同一套确定性领域规则。
- 异步事件必须持久、可重试、可审计，并允许至少一次投递。
- LLM、管理端、SDK、策略和支付通道之间必须有明确依赖方向。
- 架构需要保留未来拆分服务和引入消息队列的迁移路径。

## 决策

### 总体架构

MVP 后端采用模块化单体。模块化单体描述的是代码、数据访问和事务边界，不要求所有功能运行在同一个操作系统进程中。

- `apps/api` 和 `apps/worker` 是两个独立进程，可以分别部署和扩缩容。
- 两个进程初期使用同一个版本、同一组领域模块和同一个 PostgreSQL 数据库。
- 模块之间使用 TypeScript 接口和函数调用，不通过内部 HTTP 或消息 Broker 通信。
- `apps/web` 只承担管理与审批界面，不包含支付决策逻辑。
- PostgreSQL 是业务状态、审计事件和 Outbox 的唯一事实来源。

### 模块边界

| 模块                 | 职责                                          | 禁止事项                                           |
| -------------------- | --------------------------------------------- | -------------------------------------------------- |
| `apps/api`           | HTTP 传输、认证、输入编排、用例调用和事务协调 | 不实现支付通道细节，不允许 LLM 绕过策略层          |
| `apps/worker`        | Outbox 消费、Webhook、重试、对账和补偿任务    | 不复制 API 中的领域规则，不把内存队列作为事实来源  |
| `apps/web`           | 管理控制台和人工审批入口                      | 不直接访问数据库或支付通道                         |
| `packages/contracts` | 外部 Contract、序列化边界和兼容性规则         | 不依赖应用入口、数据库或支付通道                   |
| `packages/policy`    | Mandate、预算和交易条件的确定性判断           | 不执行网络或数据库 I/O，不接受自然语言作为支付参数 |
| `packages/payment`   | Payment Provider 接口、通道适配和规范化结果   | 不决定业务授权，不泄漏通道专有类型到 Contract      |
| `packages/config`    | 环境配置加载、校验和脱敏错误                  | 不包含业务规则或运行时密钥值                       |
| `packages/sdk-ts`    | 面向 Agent 和商户的客户端能力                 | 不依赖服务端配置、数据库或具体支付通道             |

所有 `packages/*` 禁止反向依赖 `apps/*`。应用层可以组合共享包，共享包之间只沿明确接口依赖，禁止通过通用工具模块隐藏循环依赖。

业务表由对应模块的数据访问层拥有。其他模块不得绕过公开用例直接操作其 Repository；确实需要数据库级一致性的核心关系可以使用外键和同一事务维护。

### 数据与事务

- MVP 使用单一 PostgreSQL 数据库，不使用 SQLite 作为运行时业务数据库。
- 同一业务状态转换涉及的核心写入、审计事件和 Outbox 记录必须在一个数据库事务中提交。
- 事务边界由应用用例控制，Repository 不自行开启无法组合的独立事务。
- 外部支付、Webhook 或其他网络调用不得在持有数据库事务和行锁时执行。
- 外部调用前后分别持久化明确状态，并通过幂等键、唯一约束和状态机处理重试。
- 当前使用集中迁移序列维护一个数据库；ORM、查询层和迁移工具留到 `P2-09` 单独选型。

### 异步处理

MVP 使用 Transactional Outbox，不引入 Redis、RabbitMQ、Kafka 或其他外部消息系统。

1. 业务事务在更新领域状态时，同时写入不可变的 Outbox 记录。
2. Worker 在短事务中认领待处理记录；PostgreSQL 实现应使用适合多 Worker 竞争的行级锁定方式，例如 `FOR UPDATE SKIP LOCKED`。
3. Outbox 采用至少一次投递语义。每个处理器必须使用稳定幂等键，并由数据库唯一约束或等效持久机制保证重复执行安全。
4. 成功处理后记录完成时间；失败记录尝试次数、下一次执行时间和脱敏错误分类，并采用有上限的退避重试。
5. 超过重试上限的记录进入可观察的终止状态，必须支持人工检查和显式重放，不能静默丢弃。
6. 事件包含稳定事件 ID、事件类型、Schema 版本、发生时间、聚合标识和 Trace ID；载荷不得包含支付密钥或不必要的身份数据。

Transactional Outbox 的代码实现安排在 `P5-08`，此前涉及异步副作用的设计必须保留同一事务写入 Outbox 的能力。

### 安全边界

- LLM 和 Agent Runtime 只能提交结构化 Contract，不能直接调用 Payment Provider。
- `packages/policy` 的确定性结果是支付编排的前置条件，模型输出不能扩大已签发 Mandate。
- 支付通道凭据只提供给确实需要调用通道的运行进程，不进入前端、SDK、Contract、事件或日志。
- API、Worker 和未来的运维任务使用最小数据库权限；生产角色和密钥管理在部署阶段落实。
- 审计与 Outbox 记录遵循数据最小化原则，错误信息必须脱敏。

## 被否决的方案

### 模块化单体、SQLite 与进程内任务

该方案本地成本最低，但多进程写入、行级并发控制、持久重试和 PostgreSQL 生产语义无法得到充分验证。后续迁移会同时改变数据库并发、事务和任务执行模型，对支付一致性风险过高。

### 微服务、独立 PostgreSQL 与 RabbitMQ

该方案支持更强的独立扩缩容和故障隔离，但 MVP 需要额外处理服务认证、消息 Broker、分布式追踪、跨服务一致性、版本兼容和更多密钥。当前团队规模和未经验证的流量不足以抵消这些成本。

## 后果

正面影响：

- 业务状态、审计和 Outbox 可以使用单一事务保证原子性。
- 本地调试、测试、部署和故障排查路径较短。
- API 与 Worker 可以独立运行，同时复用一致的 Contract 和领域规则。
- 不依赖云厂商专有队列，初期运行成本和供应商锁定较低。

负面影响：

- PostgreSQL 同时承担业务查询和 Outbox 轮询，需要监控连接数、索引、锁等待和积压。
- 模块隔离依赖代码审查、测试和依赖规则，不具备进程级强隔离。
- 单一数据库是共享故障域，必须在闭测前落实备份、恢复和连接保护。
- 后续拆分服务仍需要数据迁移和接口稳定化工作。

## 演进触发条件

只有满足以下一项并有监控数据支持时，才重新评估消息 Broker 或服务拆分：

- Outbox 持续积压，数据库轮询优化后仍无法满足已定义的处理时限。
- 某模块需要与其余系统显著不同的扩缩容、发布频率或故障隔离等级。
- 团队形成长期独立的模块所有权，单一发布节奏成为交付瓶颈。
- 合规或支付合作方要求支付执行具备独立网络和运行隔离。

迁移时保留 Transactional Outbox 作为数据库提交与事件发布之间的原子边界，由 Outbox Publisher 把版本化事件发送到选定 Broker。服务按照现有模块边界逐个提取，并在完成数据所有权迁移前避免双写。

## 本 ADR 不决定的事项

- ORM、SQL 查询层和数据库迁移工具，留到 `P2-09` 选型。
- Contract 运行时校验库和具体 Schema 格式，按后续 Contract 任务确认。
- 策略引擎产品、支付通道 SDK、云数据库和部署平台。
- 未来消息 Broker 的产品选择；未达到演进触发条件前不引入。
