# ADR-005：Quote 计价与签名 Profile

- 状态：已接受
- 日期：2026-08-27
- 关联决策：`D-020`

## 背景

Quote 是商户对一次服务购买给出的可携带报价，会被 Agent、策略引擎、交易核心、数据库、异步任务和 SDK 共同处理。它必须明确绑定商户与服务，允许策略引擎复算价格，在过期后不可创建新交易，并在离开原始 HTTP 请求后仍可独立验签。

MVP 只验证 API、MCP 和 Skill 服务按次购买，不需要阶梯计价、聚合账单或任意精度用量。首发市场使用人民币，但仍需明确含税价格与价外税，避免同一个 `total` 被不同组件作出不同解释。

## 计价候选与权衡

| 维度     | 固定单价、整数数量与金额明细       | 仅保存最终总额               | 通用阶梯及动态计价模型       |
| -------- | ---------------------------------- | ---------------------------- | ---------------------------- |
| 开发成本 | 低至中，可直接复算                 | 最低                         | 高，需要规则和舍入模型       |
| 运行成本 | 低                                 | 最低                         | 中，需要执行计价规则         |
| 可靠性   | 单价、数量、税费和总额可交叉验证   | 无法解释或复算总额           | 分支多，规则版本容易产生差异 |
| 安全性   | 签名覆盖全部金额因子，便于防篡改   | 总额受保护但审计证据不足     | 规则与输入都必须进入签名边界 |
| 生态     | 映射常见按次 API/MCP 服务简单      | 接入简单但表达力过低         | 更接近完整 Billing 系统      |
| 锁定     | 低，字段可映射到多数订单模型       | 低                           | 中高，绑定 AIPay 计价规则    |
| 迁移     | 后续可新增 Quote Schema 支持新模型 | 后续补明细时需改变所有消费者 | 首版即承担长期兼容和迁移成本 |

## 签名候选与权衡

| 维度     | JCS 与 Ed25519 Proof           | JWS 签名封装                 | 仅 HTTP Message Signatures   |
| -------- | ------------------------------ | ---------------------------- | ---------------------------- |
| 开发成本 | 中，可复用 Mandate Profile     | 中高，需要 JOSE 封装和解码   | 初期低                       |
| 运行成本 | 低                             | 低                           | 低                           |
| 可靠性   | 规范化后签名输入稳定           | 标准封装成熟                 | Quote 离开 HTTP 后无独立签名 |
| 安全性   | 独立域、固定算法和严格字段边界 | 需防止算法降级和 Header 误用 | 持久化和异步传递保护不足     |
| 生态     | JCS、Ed25519 有跨语言实现      | JOSE 生态最广                | 适合请求和响应传输           |
| 锁定     | 中，复用 AIPay Proof Profile   | 中，绑定 JOSE 数据模型       | 高度绑定 HTTP 传输           |
| 迁移     | JSON 保持可读、可查询          | 消费者需要理解 JWS           | 后续必须重做可携带凭证       |

## 决策

Quote V1 采用严格 camelCase JSON、固定单价、正整数数量和显式金额明细。阶梯价、动态公式、小数用量、折扣列表和税率计算不进入 MVP。

| 字段            | 规则                                                               |
| --------------- | ------------------------------------------------------------------ |
| `schemaVersion` | 固定为字符串 `1`                                                   |
| `quoteId`       | `qte_` UUIDv7                                                      |
| `merchantId`    | `mch_` UUIDv7                                                      |
| `serviceId`     | `svc_` UUIDv7                                                      |
| `unit`          | 1 至 64 位小写计量标识，如 `request`                               |
| `quantity`      | 1 至 1,000,000 的 JSON 整数                                        |
| `unitPrice`     | ADR-002 Money，必须大于零                                          |
| `subtotal`      | ADR-002 Money，必须等于 `unitPrice * quantity`                     |
| `taxBehavior`   | `inclusive` 或 `exclusive`                                         |
| `taxAmount`     | ADR-002 Money，由商户给出；AIPay 不计算税率                        |
| `total`         | ADR-002 Money，必须大于零并满足下述税费恒等式                      |
| `issuedAt`      | ADR-002 UTC 时间                                                   |
| `expiresAt`     | ADR-002 UTC 时间，必须晚于 `issuedAt`；`now >= expiresAt` 即已过期 |
| `proof`         | 与 Mandate 相同的严格 Ed25519 Proof 结构                           |

所有 Money 在 V1 中必须为 CNY。乘法、加法和输入金额均不得超过 PostgreSQL `BIGINT` 上限。

税费关系固定如下：

- `inclusive`：`total = subtotal`，且 `0 <= taxAmount <= subtotal`；`taxAmount` 是已包含在小计中的税额；
- `exclusive`：`total = subtotal + taxAmount`；`taxAmount` 是加在小计之外的税额；
- `taxAmount = 0` 对两种模式都合法；
- 商户负责税务判断与金额结果，AIPay 只验证声明值之间的确定性关系，不提供税务建议或税率引擎。

## 签名输入

Quote V1 使用 `proof.scheme = "aipay-jcs-ed25519-v1"`。签名视图包含完整 Quote，但 `proof` 中只保留 `scheme` 和 `keyId`，不包含 `proof.value`。

签名输入按以下顺序构造：

1. 使用 RFC 8785 JCS 把签名视图规范化为 UTF-8 字节；
2. 在其前面拼接 UTF-8 编码的域隔离字符串 `AIPAY-QUOTE-V1\0`；
3. 使用 `proof.keyId` 对应的商户 Ed25519 私钥签名；
4. 把 64 字节签名编码为规范无填充 base64url 并写入 `proof.value`。

验证时必须先执行结构与金额语义校验，再确认密钥属于 `merchantId` 对应商户并验证签名。商户密钥归属检查依赖身份数据，不在纯 Contract 解析器中执行。JCS 与 Ed25519 的具体实现库在 `P5-02` 前按选型门禁确认。

## 后果

- 策略引擎可以直接使用签名后的 `total`，同时复算单价、数量和税费关系。
- V1 Quote 只描述一项服务；多服务购物车必须拆分报价或通过新 Schema 引入。
- 服务目录中的计量单位必须与 Quote 的 `unit` 精确匹配，该关联在创建报价和交易时校验。
- 新增阶梯价、小数用量、折扣、币种或多税项需要新的 Schema 版本，不得给 V1 字段增加隐式含义。
- Transaction 必须引用 Quote ID，并保存用于授权判断和支付执行的最终金额快照。
