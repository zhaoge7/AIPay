# ADR-002：标识、金额与时间表示

- 状态：已接受
- 日期：2026-08-26
- 关联决策：`D-016`

## 背景

AIPay 的授权、报价、交易、支付尝试、交付和退款会跨 API、数据库、异步事件及 SDK 传递。标识、金额或时间存在多种等价表示时，容易产生对象混淆、浮点误差、签名不一致、过期判断偏差和跨语言兼容问题。

本决策为所有新 Contract 建立唯一规范表示。具体 Contract Schema 库、UUID 生成库和数据库迁移工具不在本任务中选择。

## 标识

公共资源 ID 使用三字符资源前缀、下划线和小写规范 UUIDv7：

```text
<prefix>_<lowercase-canonical-uuidv7>
mdt_01890f3e-9b4a-7cc2-98c5-7f6a1b2c3d4e
```

| 前缀  | 资源            |
| ----- | --------------- |
| `dev` | 开发者          |
| `agt` | Agent           |
| `key` | 签名密钥        |
| `mch` | 商户            |
| `svc` | 服务            |
| `mdt` | Mandate         |
| `qte` | Quote           |
| `txn` | Transaction     |
| `pat` | Payment Attempt |
| `dlv` | Delivery        |
| `rfd` | Refund          |
| `evt` | Audit Event     |
| `obx` | Outbox Event    |

- UUID 必须为版本 7，并使用 RFC 4122/9562 兼容变体位；大写、无连字符、其他 UUID 版本或错误资源前缀一律拒绝。
- 数据库存储去掉前缀后的原生 `UUID`，应用边界负责验证前缀和组合公共 ID。
- 新 ID 只能在可信服务端使用符合 UUIDv7 的密码学安全实现生成。`packages/contracts` 只负责规范和校验，不自行实现随机数或生成算法。
- 外键、日志、事件和幂等记录使用同一个底层 UUID，不创建第二套可变业务编号代替主标识。

## 金额与币种

Contract 中的金额使用以下结构：

```json
{
  "currency": "CNY",
  "amountMinor": "123"
}
```

该值表示人民币 1.23 元。

- `amountMinor` 是规范非负十进制整数字符串，只允许 `0` 或不带前导零的数字。
- 禁止负号、正号、小数点、指数、空白、千位分隔符和 JSON number。
- Contract 和事件使用字符串；TypeScript 领域计算使用 `bigint`；PostgreSQL 使用带非负约束的 `BIGINT`。
- 最大值为 PostgreSQL 有符号 `BIGINT` 最大值 `9223372036854775807`，所有边界使用同一上限。
- 通用金额允许零值。支付、退款或报价是否必须大于零由相应 Contract 的业务规则决定。
- 退款和冲正使用独立对象及方向语义，不使用负金额暗示方向。
- `currency` 使用大写 ISO 4217 代码。MVP 只支持 `CNY`，其最小货币单位位数固定为 `2`；不根据运行环境或浮点运算推断位数。
- 不同币种的金额禁止直接相加或比较。增加币种必须先登记固定的最小单位位数和通道支持情况。

数据库列对应为 `amount_minor BIGINT` 和受约束的币种代码列。具体列类型、约束名称和迁移语法在 `P2-09`、`P2-10` 落实。

## 时间与时区

所有业务时刻在 Contract 和事件中使用 UTC RFC 3339 字符串，固定三位毫秒并以大写 `Z` 结尾：

```text
2026-08-26T12:34:56.789Z
```

- 不接受时区偏移、缺少毫秒、超过毫秒的精度、小写 `z`、不存在的日期或年份 `0000`。
- PostgreSQL 使用 `TIMESTAMPTZ(3)`，读取后规范化为相同 UTC 字符串。
- 到期条件统一为 `now >= expiresAt`；等于截止时刻即已过期。
- 领域函数不得隐式读取系统时钟。调用方必须传入 `now`，生产代码使用注入时钟，测试使用固定时钟。
- 持续时间和重试间隔使用带单位的字段名及整数值，例如 `retryAfterMs`，不得使用无单位数字。
- 用户界面可以按明确的展示时区转换，但签名、存储、比较和审计始终使用规范 UTC 值。

## 校验错误

值对象解析失败时返回稳定、可分类的错误码，不在错误消息中回显原始输入。这既避免签名边界出现多种宽松解析结果，也降低日志意外记录敏感值的风险。

## 被否决的方案

- ULID、主货币单位小数字符串和保留输入偏移：可行，但金额定点解析和时间规范化路径更多，跨语言签名更容易不一致。
- 数据库连续序号、JavaScript number 和 Unix 毫秒：实现简单，但公共 ID 可枚举，金额受安全整数上限约束，时间单位也容易混用。
- JSON 浮点金额：无法精确表示全部十进制金额，禁止使用。

## 后果

- 所有边界需要显式解析，不能把任意字符串或 number 当作已验证值。
- 公共 ID 与数据库 UUID 之间需要可测试的前缀转换。
- SDK 必须保留金额和时间的字符串表示，不能自动转换为浮点数或本地时间字符串。
- UUID 生成、数据库映射和具体 Contract Schema 后续实现时必须遵守本 ADR。
